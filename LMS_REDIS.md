# Redis: кеш с TTL, Pub/Sub и очередь задач

**Код работы:** [redis_lab](redis_lab).
**Интеграционные тесты:** [test_redis_lab.py](test_redis_lab.py).

## Подготовка

Команды выполняются из корня репозитория. Используется библиотека `redis-py`
(пакет `redis`, уже включён в `requirements.txt`).

```bash
docker compose -p specdb up -d redis
source .venv/bin/activate
pip install -r requirements.txt
```

Для нового окружения сначала выполните `python3 -m venv .venv`.
Подключение по умолчанию — `redis://localhost:6379/0`.
Другой адрес задаётся переменной `REDIS_URL`.

## 1. Кеш с TTL

Файл: [redis_lab/cache.py](redis_lab/cache.py).

Класс `JsonCache` реализует cache-aside: сначала читает Redis, при промахе
вызывает функцию-источник и сохраняет результат в JSON с TTL.
Значение и срок жизни задаются одной командой `SET ... EX`, поэтому не возникает
промежутка между записью ключа и назначением TTL. Попадание в кеш не продлевает
его срок жизни. `invalidate` позволяет удалить отдельное значение.

Ключевой фрагмент:

```python
cached = self.client.get(redis_key)
if cached is not None:
    return json.loads(cached)
value = loader()
self.client.set(redis_key, json.dumps(value, ensure_ascii=False), ex=ttl_seconds)
return value
```

Запуск:

```bash
python -m redis_lab.cache --ttl 3
```

Первый запрос вызывает источник, второй получает сохранённое значение. После
ожидания TTL источник вызывается повторно. В демонстрации источником служит
функция со счётчиком вызовов; вместо неё можно передать чтение из БД или API.
Значения `null`, `false`, `0` также кешируются корректно.
Кеш простой: параллельные промахи могут одновременно вызвать источник.

Пример проверенного вывода с `--ttl 1`:

```text
Чтение из источника, вызов №1
Первый запрос: {'id': 1, 'name': 'Анна', 'source_call': 1}
Повторный запрос: {'id': 1, 'name': 'Анна', 'source_call': 1}
TTL в Redis: 1
Чтение из источника, вызов №2
После истечения TTL: {'id': 1, 'name': 'Анна', 'source_call': 2}
```

## 2. Pub/Sub — два отдельных скрипта

- [redis_lab/subscriber.py](redis_lab/subscriber.py) — подписывается на канал и читает сообщения.
- [redis_lab/publisher.py](redis_lab/publisher.py) — публикует JSON с текстом и временем UTC.

Терминал №1 (дождитесь строки «Подписка готова»):

```bash
source .venv/bin/activate
python -m redis_lab.subscriber
```

Терминал №2:

```bash
source .venv/bin/activate
python -m redis_lab.publisher "Заказ оплачен"
```

Канал по умолчанию — `lab:events`; оба скрипта принимают `--channel`.
Подписчик завершится по Ctrl+C или после заданного числа сообщений:
`python -m redis_lab.subscriber --count 1`.

Используются `client.publish`, `client.pubsub`, `subscribe` и `listen`.
Redis Pub/Sub не хранит историю: сообщение до подключения подписчика будет
потеряно для него. Число, возвращаемое `publish`, отражает подключённых
подписчиков, а не подтверждение обработки сообщения их кодом.

## 3. Очередь задач и обработчик

- [redis_lab/task_queue.py](redis_lab/task_queue.py) — класс `TaskQueue` и скрипт постановки задачи.
- [redis_lab/worker.py](redis_lab/worker.py) — отдельный процесс-обработчик.

Задача содержит уникальный UUID, тип `sum` и список целых чисел.
Производитель добавляет JSON в Redis List командой `RPUSH`. Обработчик извлекает
задачу через блокирующий `BLPOP`: это FIFO, ожидание не создаёт цикл частого опроса.

```python
# Постановка
self.client.rpush(self.key, json.dumps(task))

# Получение и выполнение
item = self.client.blpop(self.key, timeout=2)
task = json.loads(item[1])
value = sum(task["numbers"])
```

В рабочем коде также есть проверки формата и обработка пустой очереди.
Некорректная задача возвращает `status="failed"`, следующая задача продолжает
обрабатываться. Успех возвращает `status="done"` и вычисленное значение.
Результаты задач с корректным id сохраняются отдельными ключами с TTL 300 секунд.

Добавление задачи (можно до запуска обработчика):

```bash
python -m redis_lab.task_queue 10 20 30
```

Запуск обработчика:

```bash
python -m redis_lab.worker
```

Для одной попытки чтения с ожиданием до 2 секунд:

```bash
python -m redis_lab.worker --once
```

Ожидаемый результат — `{"id": "...", "status": "done", "value": 60}`.
Оба скрипта принимают `--queue`; по умолчанию это `lab:tasks`.
Производитель печатает ключ результата. Посмотреть его можно через
`TaskQueue.get_result(task_id)` либо командой, подставив выведенный id:

```bash
docker compose -p specdb exec redis redis-cli GET lab:tasks:result:ID_ЗАДАЧИ
```

Это простая очередь без подтверждений и повторной доставки: `BLPOP` удаляет
задачу до выполнения. Если процесс упадёт после извлечения, задача может быть
потеряна; если Redis недоступен при записи результата, результат не сохранится.
Сохранение Redis на диск (AOF в Docker Compose) не устраняет этот промежуток.
Несколько обработчиков могут извлекать разные задачи, но порядок завершения
тогда не гарантирован. Для задания используется один обработчик.

## Проверка и сдача

```bash
python -m unittest -v test_redis_lab
```

Шесть интеграционных тестов проверяют:

- попадание в кеш и реальное истечение TTL;
- кеширование пустых значений и ошибку источника;
- порядок FIFO и сохранение результата с TTL;
- продолжение обработки после некорректной задачи;
- отдельные процессы производителя задач и обработчика;
- отдельные процессы publisher/subscriber и отсутствие истории Pub/Sub.

Тесты используют случайный префикс и удаляют только собственные ключи,
без `FLUSHDB`/`FLUSHALL`.

В ЛМС можно приложить ссылку на каталог `redis_lab` или этот файл с пояснениями
и ссылками на код. Репозиторий приватный — преподавателю нужен доступ.
Альтернатива: скриншоты `cache.py`, `publisher.py`, `subscriber.py` и `task_queue.py`.
