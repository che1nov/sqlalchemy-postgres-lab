# Чернов Илья — Итоговое задание — Трекер задач

**Студент:** Чернов Илья. **Дисциплина:** Спецглавы баз данных.

Вариант 1: персональный трекер задач. FastAPI, SQLAlchemy 2, PostgreSQL 16, Alembic,
pandas, matplotlib, pytest. Python **3.11+**. Для проверки без установки Python
предусмотрен Docker Compose. Интерфейс демонстрации - Swagger UI `/docs`.

## Быстрый запуск

Из корня репозитория:

```bash
cd task_tracker
docker compose -p specdb-tracker up --build -d --wait
```

Откройте <http://localhost:8000/docs>. Проверка готовности:
<http://localhost:8000/health>. БД сохраняется в именованном томе `postgres_data`.
Команда `docker compose -p specdb-tracker down` останавливает стенд, сохраняя данные.
Порт опубликован только на `127.0.0.1`.

Приложение локально, PostgreSQL в Docker, из каталога `task_tracker`:

```bash
python3.11 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements-dev.txt -c requirements.lock
docker compose -p specdb-tracker up -d --wait postgres
alembic upgrade head
uvicorn app.main:create_app --factory --host 127.0.0.1 --port 8000
```

В Windows активация: `.venv\Scripts\activate`. `requirements.lock` фиксирует
проверенные версии зависимостей и используется как constraints для pip.
Приложение не создаёт таблицы при запуске: сначала нужно применить миграции.
Docker делает это перед запуском HTTP-сервера.

`TRACKER_DATABASE_URL` по умолчанию:
`postgresql+psycopg://tracker:tracker_local@localhost:5434/tracker`.
В контейнере хост - `postgres`, порт - `5432`. Для своей PostgreSQL задайте
URL через переменную окружения. Порт стенда `5434` не конфликтует с прошлыми
лабораторными. Учебный пароль `tracker_local` предназначен только для локального
стенда; PostgreSQL опубликован только на `127.0.0.1`. Не используйте БД предыдущих
лабораторных: у этого сервиса собственные таблицы и история миграций.

## Демонстрация в Swagger UI

1. `POST /auth/register`: `{"username":"student","password":"my-study-password-123"}`.
2. `POST /auth/login`: те же данные; скопируйте `access_token`.
3. Нажмите **Authorize** вверху `/docs`, вставьте только значение токена.
4. `POST /tasks`: `{"title":"Подготовить ERD","topic":"Базы данных"}`.
5. `PATCH /tasks/{id}`: `{"status":"in_progress"}`, затем `{"status":"done"}`.
6. `GET /tasks`: попробуйте `status=done`, `topic=Базы данных`, `q=ERD`.
7. `GET /analytics/tasks`: последовательно `group_by=status`, `topic`, `assignee`.
8. `GET /analytics/tasks.png`: получите PNG-график с теми же фильтрами.
9. `DELETE /tasks/{id}` и `POST /auth/logout`: проверьте удаление и отзыв токена.

`GET /users` возвращает ID и логины зарегистрированных пользователей для выбора
исполнителя. `assignee_id: null` снимает назначение. Назначение - учётный атрибут:
оно **не даёт исполнителю доступ к задаче**. Все операции разрешены только владельцу.
Это персональный трекер с учётом исполнителей, без командных пространств и ролей.

## Автоматическая HTTP-демонстрация

В другом терминале, при работающем сервере:

```bash
cd task_tracker
python3 -m scripts.demo
```

Или внутри Docker без локального Python:

```bash
docker compose -p specdb-tracker exec api python -m scripts.demo --output /tmp/tracker-demo
```

Сценарий создаёт отдельный случайный аккаунт, выполняет CRUD, проверяет фильтры,
сохраняет три PNG-графика и JSON, затем выходит и проверяет, что токен отозван.
Каждый запуск оставляет 12 учебных задач нового аккаунта. Пароли и токены не
записываются в файлы. Готовые результаты: [output/demo](output/demo).

## API

Все маршруты, кроме регистрации, входа, health и документации, требуют
`Authorization: Bearer <token>`.

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/auth/register` | Регистрация, 201; занятый логин - 409 |
| POST | `/auth/login` | Выдать токен на 24 часа |
| POST | `/auth/logout` | Отозвать текущий токен, 204 |
| GET | `/users/me` | Текущий пользователь |
| GET | `/users` | Справочник исполнителей, `limit`, `offset` |
| POST | `/tasks` | Создать задачу со статусом `new`, 201 |
| GET | `/tasks` | Список и общее число результатов |
| GET | `/tasks/{id}` | Получить задачу |
| PATCH | `/tasks/{id}` | Изменить переданные поля / статус |
| DELETE | `/tasks/{id}` | Удалить задачу, 204 |
| GET | `/analytics/tasks` | Статистика JSON |
| GET | `/analytics/tasks.png` | Диаграмма PNG |

Список: `status`, `topic` (точное совпадение), `assignee_id`, `q` (подстрока в
заголовке или описании); фильтры соединяются через AND. Поиск использует SQL LIKE
с экранированием `%` и `_`; поиск учитывает регистр (PostgreSQL LIKE).
Порядок: ID по убыванию. `limit` 1-100
(по умолчанию 20), `offset >= 0`. `total` - число до пагинации.

Аналитика принимает те же фильтры, без пагинации; `group_by` - только `status`,
`topic`, `assignee`. Для исполнителя ключ - строка ID, отсутствие - `unassigned`.
Процент завершения = `done / total * 100`, округление до двух знаков, для пустого
набора - 0. Отменённые задачи входят в `total`. Все четыре статуса присутствуют
в группировке по статусам, включая нулевые. JSON содержит все группы; диаграмма
показывает 20 наиболее крупных, длинные подписи сокращаются только на графике.

Ошибки: 401 - нет действующего токена; 404 - задача отсутствует или чужая;
409 - занятый логин; 422 - неверные поля или исполнитель; 503 - ошибка БД без
раскрытия SQL и реквизитов. `PATCH {}` и `null` в обязательных полях запрещены.
Передавать `owner_id`, ID задачи и служебные даты в теле запрещено.

## Модель, миграции и структура

Подробности: [docs/data-model.md](docs/data-model.md), включая ERD, ограничения,
индексы и правила удаления. Все даты хранятся и возвращаются в UTC, без смещения.

```text
app/
  main.py         сборка приложения, зависимости, обработка ошибок
  api.py          HTTP, структурная валидация, вызовы сервисов
  schemas.py      входные и выходные DTO Pydantic
  services.py     AuthService, TaskService, права доступа, транзакции
  repository.py   параметризованные SQLAlchemy-запросы
  models.py       таблицы и статусы
  db.py           PostgreSQL engine и сессии
  analytics.py    pandas-агрегации, matplotlib PNG
migrations/       обратимая миграция Alembic
tests/            unit, HTTP и интеграционные тесты БД
scripts/          HTTP-демонстрация и сборка архива
docs/             ERD, сценарий защиты, соответствие критериям
output/           графики и JSON
```

Архитектура ограничена handler → service → repository. Интерфейсы, DDD и CQRS
для такого CRUD не нужны. ORM-модель используется внутри простого сервиса,
а transport DTO отделены от неё. Сервисы фиксируют транзакции, репозиторий делает
`flush`, но не `commit`. Закрытие сессии откатывает незавершённую транзакцию.
В Python используется стандартный `logging`, logger передаётся в фабрику приложения.

Статусы: `new`, `in_progress`, `done`, `cancelled`. Владелец может перевести задачу
в любой из них, в том числе повторно открыть завершённую. Более строгий workflow
в задании не задан. При конкурентном редактировании одного поля последнее
зафиксированное изменение побеждает. PostgreSQL обеспечивает транзакции и
целостность; аналитика загружает отфильтрованные строки в pandas, поэтому
не рассчитана на миллионы задач.

## Тесты и миграции

```bash
docker compose -p specdb-tracker --profile tools run --build --rm tests
```

Либо в активном Python-окружении при запущенной PostgreSQL:

```bash
python -m pytest -q
alembic check
```

Тесты не требуют работающего HTTP-сервера и не используют пользовательскую БД.
Каждый интеграционный тест создаёт отдельную PostgreSQL-БД `tracker_test_<uuid>`,
применяет настоящую миграцию и удаляет только эту БД после теста. Для подключения
используется `TRACKER_TEST_DATABASE_URL` (по умолчанию:
`postgresql+psycopg://tracker:tracker_local@localhost:5434/postgres`). Тестовому
пользователю нужна привилегия CREATEDB; локальный Docker-пользователь её имеет.
Проверяются CRUD, фильтры, пагинация, изоляция владельцев, Argon2,
отзыв и истечение токена, ошибки валидации, SQL-инъекции, группировки, PNG,
FK/CHECK-ограничения, каскады, rollback и цикл upgrade → downgrade → upgrade.
Unit-тесты сервисов используют простые mock-зависимости без отдельных интерфейсов.

Для изменения схемы создавайте новую миграцию:

```bash
alembic revision --autogenerate -m "describe schema change"
alembic upgrade head
alembic check
```

`alembic downgrade base` удаляет таблицы и данные: используйте только на
одноразовой БД. Проверка отката уже входит в тесты и работает на временной БД.
В репозитории добавлен workflow `.github/workflows/task-tracker.yml` с pytest
и проверкой запуска контейнера. Он запускается после отправки изменений в GitHub.

## Защита

- Пароли: Argon2id с солью; минимум 10, максимум 128 символов; пароль не возвращается.
- Случайный Bearer-токен: 32 байта энтропии; в БД только SHA-256 хеш, срок - 24 часа.
- Выход удаляет серверную сессию; повторное использование и просроченный токен дают 401.
- Для отсутствующего пользователя также выполняется Argon2-проверка фиктивного хеша.
- Значения связываются через SQLAlchemy, SQL из пользовательских строк не собирается.
- Поля группировки ограничены Literal; передать произвольное имя столбца нельзя.
- Выборка, изменение, удаление и аналитика всегда ограничены владельцем.
- PostgreSQL FK обеспечивает связи; CHECK защищает статус и непустые поля.
- Ошибки валидации не возвращают сырые входные значения; SQL и пароли не логируются.

Область применения - локальная учебная демонстрация. Для публичного размещения
нужны HTTPS и ограничение частоты запросов к регистрации/входу на reverse proxy.
Истёкшие сессии отвергаются, но автоматически не удаляются; для долгой эксплуатации
нужна периодическая очистка. Секретов для JWT и внешних сервисов здесь нет.
